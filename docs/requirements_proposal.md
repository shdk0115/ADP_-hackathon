# 요건 정의 및 서비스 기획안

**프로젝트명:** ADP — Agentic OpenSearch Indexing Pipeline
**팀:** AIR Unit
**작성일:** 2026-05-09
**버전:** 1.0

## 1. 문제 정의 (Problem Statement)

### 1.1 시장 배경

기업의 사내 RAG(Retrieval-Augmented Generation) 도입은 폭발적으로 증가하고 있다.
복지 규정·전결권자 리스트·매뉴얼·정책 문서 등 **비정형 한국어 도메인 문서**를 LLM과 결합하여
직원의 자연어 질의에 정답을 돌려주는 시나리오가 표준이 되어가고 있다.

그러나 실무에서 RAG를 한 번이라도 구축해본 팀은 다음 문제에 부딪힌다.

### 1.2 핵심 문제 3가지

| # | 문제 | 결과 |
|---|---|---|
| **P1** | **인덱스 설계가 흑마법이다.** 어떤 analyzer? nori? 형태소 분해? HyDE 적용? Hybrid 비율? — 정답이 데이터마다 다르다. | RAG 엔지니어 1~2주 시행착오, 그래도 정확도 50~70%대에서 정체 |
| **P2** | **점진적 개선의 가시화가 안 된다.** "베이스라인 대비 얼마나 좋아졌는가?"를 임원/PM에게 설명할 객관적 숫자가 없다. | RAG 프로젝트가 ROI 검증 단계에서 좌초 |
| **P3** | **실패 원인이 모호하다.** 정확도가 안 나오면 "데이터 문제"인지 "파이프라인 문제"인지 사람이 일일이 추적해야 한다. | 데이터 오너 vs 엔지니어 책임 핑퐁, 디버깅 비용 폭증 |

### 1.3 우리가 풀고자 하는 것

**"한국어 도메인 문서를 던지면, RAG 인덱싱 전략을 자동으로 결정하고, 점진적으로 정확도를 올리며, 실패 원인까지 자동 진단하는 파이프라인."**

## 2. 솔루션 개요 (Solution)

### 2.1 핵심 아이디어 — V1 → V2 → V3

```
        V1 (Baseline)              V2 (Agentic)             V3 (Full Stack)
   ┌──────────────────┐      ┌─────────────────┐      ┌────────────────────┐
   │ standard text    │  →   │ + LLM 키워드     │   →  │ + Nori 형태소        │
   │ + vector search  │      │   본문 보강       │      │ + DCR 도메인 사전     │
   │                  │      │                  │      │ + HyDE 의미 확장      │
   └──────────────────┘      └─────────────────┘      └────────────────────┘
        ~40%                       ~70%                      ~95%
```

각 단계가 무엇을 추가했고 왜 점수가 올라가는지가 **숫자와 logic으로 추적 가능**.

### 2.2 차별점

| | 일반 RAG 솔루션 | **본 솔루션 (ADP)** |
|---|---|---|
| 인덱싱 전략 | 사람이 결정 | **LLM 에이전트가 데이터를 보고 결정** |
| 개선 흐름 | 한 번에 빌드 | **V1 → V2 → V3 단계적 빌드 + 점수 비교** |
| 실패 진단 | 사람이 로그 분석 | **LLM이 데이터 결함 vs 파이프라인 결함 자동 분류** |
| 약어/유의어 | 사전 수동 등록 | **LLM이 본문에서 자동 추출** |
| HyDE | 별도 구현 | **자동: 요약 + QA 매칭으로 임베딩 풍성화** |
| 한국어 형태소 | 수동 nori 설정 | **DCR 사전을 본문에서 자동 생성** |

### 2.3 한 줄 요약

**"엔지니어가 1주일 걸려 만들 RAG 인덱싱 전략을, 에이전트가 30초만에 만들고, 그 효과를 V1 → V2 → V3 점수 차이로 임원에게 설명한다."**

## 3. 비즈니스 가치 (Business Value)

### 3.1 정량적 가치

| 지표 | Before (수동) | After (ADP) | 절감 |
|---|---|---|---|
| 초기 RAG 구축 시간 | 7~14일 | **30초~3분 (자동)** | **>99%** |
| 정확도 (한국어 도메인) | 50~70% | **90%+ (V3)** | **+20~40%p** |
| 인덱싱 전략 의사결정 비용 | 시니어 RAG 엔지니어 5인일 | **0** | 전액 절감 |
| 데이터 결함 진단 시간 | 평균 2~4시간/케이스 | **즉시 자동** | 시간 단축 |

### 3.2 정성적 가치

- **임원 설득 가능**: V1/V2/V3 점수 막대그래프 한 장으로 "AI 투자 효과"를 시각화
- **데이터 오너 책임 분리**: Sanity Diagnosis가 "데이터 문제 (당신 책임) vs 파이프라인 문제 (엔지니어 책임)"를 명시
- **반복 가능**: 새로운 도메인 문서마다 동일 파이프라인을 그대로 실행

### 3.3 시장 적용 분야

1. **HR / 사내 정책**: 복지 규정, 전결권, 휴가 규정, 보안 정책
2. **법무 / 계약**: 약관, 사규, 특수 계약 검토
3. **금융**: 상품 약관, 컴플라이언스 매뉴얼
4. **의료**: 의약품 정보, 처방 가이드라인 (한국어 의료 용어)
5. **고객 지원**: FAQ, 매뉴얼, 트러블슈팅 가이드

## 4. 사용자 시나리오 (User Stories)

### Persona A — 김현우 (인사팀 RAG 도입 PM)
**Context:** 회사 복지 규정을 챗봇에 연동해 직원 문의를 자동 응답하려 함. 데이터는 PDF로 받았고, 이미 QA 시트도 만들어놨음. 그런데 RAG 엔지니어가 부재.

**Pain:** "어떤 OpenSearch 매핑을 써야 하지? nori 써야 하나? 키워드 추출은? 직접 다 못 하겠다."

**Solution flow:**
1. Streamlit UI에 **복지규정.pdf + qa_시트.xlsx** 업로드
2. "RUN PIPELINE" 클릭
3. 30초 후 V1=42%, V2=68%, V3=92% 막대그래프 + 전략 결정 로그 표시
4. "이 데이터에는 V3(nori + DCR + HyDE) 인덱싱이 최적이고, 92% 정확도 달성 가능"이라는 결과를 임원에게 그대로 제출
5. 운영팀은 V3 인덱스 설정을 그대로 프로덕션에 복사

**Value:** 김현우는 RAG 엔지니어 없이도, 1주일 → 5분으로 의사결정 완료.

---

### Persona B — 이지민 (시니어 RAG 엔지니어)
**Context:** 새로운 도메인(법무팀 약관 검토) 프로젝트에 투입. 처음 보는 데이터.

**Pain:** "데이터 보고 어떤 chunking 전략·analyzer·HyDE 조합이 좋을지 감이 안 잡힌다. 하나하나 실험하기 시간 낭비."

**Solution flow:**
1. 약관 PDF + 평가용 QA 50개 업로드
2. ADP가 자동으로 V1/V2/V3 빌드 + 점수
3. **decision_log** 확인: "ko_ratio 0.92 → use_analyzer:true, semantic_complexity high → use_hyde:true"
4. **V3 인덱스가 어떤 매핑을 썼는지** 코드 그대로 복사 → 프로덕션 적용
5. 추가 튜닝 필요한 부분만 수동 작업

**Value:** 이지민의 시행착오 시간을 80% 단축. 동시에 자동 결정의 근거를 인지하고 신뢰함.

---

### Persona C — 박세영 (데이터 오너 / 인사팀)
**Context:** 자기가 만든 복지 규정 PDF가 RAG 평가에서 70%밖에 안 나옴. RAG팀이 "데이터 문제 같다"고 함.

**Pain:** "어디가 문제인지 RAG팀이 알려주지 않으면 모른다. 매번 미팅 잡고 분석 부탁해야 함."

**Solution flow:**
1. ADP가 V3에서도 70% 미달 → 자동으로 **Data Sanity Diagnosis** 실행
2. UI에 카드로 표시:
   - "Q1: 야간 택시비. 본문에는 40,000원으로 적혀있으나 QA는 30,000원이 정답. → **DATA_MISMATCH**, 데이터 오너가 본문 수정 필요"
   - "Q4: 도서구입비. 본문에 '지원 중단'으로 적혀있으나 QA는 50,000원이 정답. → **DATA_MISMATCH**"
3. 박세영은 자기 PDF를 직접 수정 → 재실행 → 95% 달성

**Value:** 데이터 오너가 RAG 엔지니어를 거치지 않고 자기 책임 영역의 문제를 자가 진단/수정.

## 5. 기능 요건 (Functional Requirements)

### F1. 입력 (Input)
- F1.1 Raw 데이터 업로드: **PDF / Excel(.xlsx, .xls) / CSV / TXT** 지원
- F1.2 QA 시트 업로드: **Excel / CSV / PDF** 지원 (PDF는 LLM이 자동 QA 추출)
- F1.3 사용자 프롬프트 입력 (사용 목적 명시)
- F1.4 한국어 인코딩 자동 처리 (utf-8 / cp949 / euc-kr)
- F1.5 컬럼명 변형 자동 정규화 (`질문 (User Question)` → `question`)

### F2. 데이터 분석 에이전트 (Agent)
- F2.1 데이터 프로파일링: 언어/구조/도메인/노이즈 자동 판정
- F2.2 인덱싱 전략 결정: index_version / use_analyzer / use_keyword / use_hyde / use_dcr
- F2.3 결정 근거 로그 (decision_log) 출력
- F2.4 LLM 호출 실패 시 fallback 적용 + 사유 노출
- F2.5 점수 미달 시 전략 재결정 (Refinement)

### F3. 인덱스 빌드 (Pipeline)
- F3.1 V1: 표준 text + vector hybrid 인덱스
- F3.2 V2: LLM 키워드 추출 + 통합 텍스트 인덱스
- F3.3 V3: nori + DCR + HyDE + 벡터 후 termvectors re-rank
- F3.4 각 단계 idempotent (재실행 시 인덱스 재생성)

### F4. 평가 (Evaluation)
- F4.1 QA 시트 자동 평가
- F4.2 V1/V2/V3 별 정확도 산출
- F4.3 실패 질문에 대한 패턴 분석 (DATE/ENTITY/CONDITIONAL/TABLE)
- F4.4 목표 점수 미달 시 Data Sanity Diagnosis

### F5. UI (Streamlit)
- F5.1 파일 업로드 폼
- F5.2 실시간 실행 로그 (터미널 스타일)
- F5.3 V1/V2/V3 점수 막대그래프
- F5.4 Strategy decision_log 카드
- F5.5 Data Sanity 진단 카드
- F5.6 실패 시 traceback 자동 노출

## 6. 비기능 요건 (Non-Functional Requirements)

| # | 항목 | 목표 |
|---|---|---|
| NFR-1 | 응답 시간 | 단일 파이프라인 실행 ≤ 3분 (1MB 이하 문서, QA 10건 기준) |
| NFR-2 | 임베딩 캐시 | 동일 chunk/쿼리 재호출 시 ≥ 1000× 속도 향상 (LRU 적용) |
| NFR-3 | LLM 실패 내성 | 모든 LLM 호출은 max 3회 retry + fallback 적용 |
| NFR-4 | 에러 가시성 | 실패 시 streamlit에 traceback + raw response 자동 표시 |
| NFR-5 | 한국어 지원 | 본문/질문/정답 모두 한국어 처리 (utf-8/cp949/euc-kr) |
| NFR-6 | 외부 의존 최소화 | Bedrock + OpenSearch 외 추가 인프라 없음 |
| NFR-7 | 보안 | AWS 자격증명은 .env로 관리, 코드에 하드코딩 금지 |

| 지표 | 목표 |

| LLM 호출 fallback 발생률 | < 5% |
| 임베딩 cache hit율 | > 70% (chunk + query 합산) |
| 데이터 결함 자동 진단 정확도 | > 80% (RAG팀 수동 진단과 일치) |

### 7.3 비즈니스 KPI

| 지표 | 목표 |
|---|---|

| 데이터 오너 자가 수정 비율 | Sanity 진단 표시된 항목의 **80%** 이상 |

## 8. 리스크 및 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| LLM(Bedrock) 호출 실패 | Strategy fallback → V1=V2=V3 | retry 3회 + DEFAULT_ANALYSIS_RESULT, 에러 사유 stdout 노출 |
| OpenSearch 응답 지연 | 시연 중 timeout | bulk size 조절, k-NN k 파라미터 튜닝 |
| 임베딩 비용 증가 | Bedrock 비용 폭증 | LRU cache (4096) + 동일 텍스트 차단 |
| 한국어 형태소 분해 오류 | V3에서 wrong tokenization | nori decompound_mode 자동 선택 + DCR 사전 보강 |
| QA 시트 표기 불일치 | 평가가 false-negative 발생 | substring 매칭 + 인코딩 폴백 + 컬럼명 정규화 |
